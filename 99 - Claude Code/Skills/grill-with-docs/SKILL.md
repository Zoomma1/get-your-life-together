## Domain awareness

This skill reads its domain context from **whatever the session-start hook already injected** into this conversation — it does not go hunting for a separate doc first. {USER_NAME}'s `load-project-context.sh` hook loads, at session start, the context for the current project:

- **Dev-repo session** (cwd is a code repo): `~/.claude/project-contexts/<slug>/README.md` *and* `CONTEXT.md` if present, where `<slug>` = `basename "$PWD"`. This is the primary case.
- **Vault session** (cwd is the vault or `$HOME`): the vault-context files.

So the project's existing codebase context and domain language are **already in your context window** when this skill runs. Read them there first — don't re-fetch.

The dev repo (your cwd) stays clean — nothing is ever written into it.

### Where resolved terms are persisted

Persist resolved terms into the project-contexts glossary, so the hook re-injects them next session:

```
~/.claude/project-contexts/<slug>/
├── README.md   ← codebase context (generated by /prepare-project-for-agent; hook cats it)
└── CONTEXT.md  ← domain glossary (this skill maintains it; hook cats it too)
```

`<slug>` = `basename "$PWD"`. Create `CONTEXT.md` lazily — only when the first term is resolved.

> **Store convention** (ADR-109): the glossary lives in the **store** (`~/.claude/project-contexts/<slug>/CONTEXT.md`), never in the target repo. This instance of the skill intentionally diverges from the online SKILL.md (mattpocock/skills) which pointed to a `CONTEXT.md` alongside the repo README — do not re-synchronize without verifying that the store convention is preserved.

**Fallback** — if there is no `~/.claude/project-contexts/<slug>/` directory (project never prepared for an agent), fall back to the vault layout `<vault>/04 - Projects/<Projet>/claude-code/CONTEXT.md` + `ADR/INDEX.md`. If you can't tell which project the repo maps to, ask before touching any doc.

## During the session

### Challenge against the glossary

When the user uses a term that conflicts with the existing language in `CONTEXT.md`, call it out immediately. "Your glossary defines 'cancellation' as X, but you seem to mean Y — which is it?"

### Sharpen fuzzy language

When the user uses vague or overloaded terms, propose a precise canonical term. "You're saying 'account' — do you mean the Customer or the User? Those are different things."

### Discuss concrete scenarios

When domain relationships are being discussed, stress-test them with specific scenarios. Invent scenarios that probe edge cases and force the user to be precise about the boundaries between concepts.

### Cross-reference with code

When the user states how something works, check whether the code agrees. If you find a contradiction, surface it: "Your code cancels entire Orders, but you just said partial cancellation is possible — which is right?"

### Update CONTEXT.md inline

When a term is resolved, update `~/.claude/project-contexts/<slug>/CONTEXT.md` (`<slug>` = `basename "$PWD"`) right there. Don't batch these up — capture them as they happen. Create it lazily if it doesn't exist. Use the format in [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md).

`CONTEXT.md` should be totally devoid of implementation details. Do not treat `CONTEXT.md` as a spec, a scratch pad, or a repository for implementation decisions. It is a glossary and nothing else.

### Offer ADRs sparingly

Only offer to create an ADR when all three are true:

1. **Hard to reverse** — the cost of changing your mind later is meaningful
2. **Surprising without context** — a future reader will wonder "why did they do it this way?"
3. **The result of a real trade-off** — there were genuine alternatives and you picked one for specific reasons

If any of the three is missing, skip the ADR. When all three hold, **create it by invoking the `/create-adr` skill** — it resolves project vs transverse scope, vault placement, numbering and `INDEX.md` update. Never write ADR files by hand. See [ADR-FORMAT.md](./ADR-FORMAT.md) for what qualifies.
